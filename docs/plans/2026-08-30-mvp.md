# aura-overlay MVP Implementation Plan

**Goal:** A resident tray app that rings project windows in their repo colors: automatic for terminals with live aura sessions, hotkey-tagged for everything else.
**Prerequisites:** aura Lane A installed (state.json exists); spike verdicts in `aura/docs/LANE-B.md` (renderer PASS, detection PASS).
**Estimated scope:** 6 steps.

Constraints that bind every step: CLAUDE.md rules 1-8 (contract pinned to aura, state.json read-only, raw Win32 overlays, zero deps, fail silent, under 3% CPU at 10 rings).

## Step 2: Renderer core (rings from a file)
**Files:** `src/renderer-win.ps1`
**What:** Grow the spike renderer into a multi-ring host: one window class, a ring registry keyed by target hwnd, 30 ms WM_TIMER tick that (a) reloads `rings.json` when mtime changes and reconciles (create/destroy/recolor in place), (b) tracks each ring's target (rect move/resize, minimize hide, restore show, target-death destroy). Entries are `{hwnd, pid, hex}`; before creating a ring the renderer requires `IsWindow(hwnd)` AND `GetWindowThreadProcessId(hwnd) == pid` (hwnds recycle; a stale entry must never ring a stranger's window), and the tick destroys a ring the moment either check fails. `-RingsFile <path>` parameter so tests use a scratch file. No tray, no hotkeys, no brain yet.
**Verify:** Hand-written rings.json against two scratch windows (Notepad, mspaint): both rings pixel-probe to their exact hex; editing the file live recolors one ring and removes the other within ~1 s; an entry with a dead hwnd and an entry with a live hwnd but wrong pid both produce NO ring and no error; minimize/restore and close behave as in the spike; foreground hwnd unchanged across renderer start and every reconcile; CPU with 2 rings idle under 1%.
**Commit:** `feat: multi-ring renderer host driven by rings.json`

## Step 3: Brain (identity to rings)
**Files:** `src/brain.js`, `src/detect-win.ps1` (adapted from the aura spike)
**What:** The decision loop from ARCHITECTURE "Data Flow": scan windows, identity ladder (resolved tags -> aura-state terminals minus rainbow-owned -> palette processes -> nothing), `colorsFor`, atomic rings.json write on change, entries `{hwnd, pid, hex}`. `--once` prints the ring set and exits (testable without the renderer); default mode loops every 2 s and exits when the pid passed as `--parent-pid` is gone (a crashed renderer must not leave a brain running). Test flags: `--dir <path>` (runtime dir override) and `--state <path>` (aura state.json override). `config.json` defaults written on first run: `{ "paletteProcesses": ["chrome", "slack"] }`.
**Verify:** `node src/brain.js --once` twice, 2 s apart: byte-identical output; the WT window with live sessions maps to the exact frameHex stored in aura state.json; rainbow-owned windows absent from the set; chrome windows present with one shared palette hex; then a real delta, not just stability: add a scratch process to paletteProcesses via a test config, open its window, run again (it appears with the expected hex), close it, run again (it is gone); `git diff src/color.js` empty.
**Commit:** `feat: brain identity loop writing rings.json`

## Step 4: Wiring + tray (resident app)
**Files:** `src/renderer-win.ps1` (tray + brain child + singleton), `bin/start.js`
**What:** Renderer gains the NotifyIcon (tooltip "aura-overlay", context menu: Quit) and spawns the brain as a child at startup with `--parent-pid`, killing it on quit; Quit destroys all rings then exits the message loop. Singleton: the renderer takes a named mutex at startup and exits silently (one local log line) if it is already held. `bin/start.js` launches the renderer hidden via the Start-Process double-hop and prints the pid; `--stop` writes `stop.flag` into the runtime dir; the renderer's tick sees it, deletes it, and quits cleanly. No new Win32 IPC surface: stop rides the same polled-file pattern as rings.json.
**Verify:** `node bin/start.js` on the live desktop: rings appear on the expected windows within ~3 s; tray icon present; a SECOND `node bin/start.js` leaves exactly one renderer + one brain (singleton holds); `node bin/start.js --stop` removes every ring, the tray icon, and BOTH processes (verify by pid); then a crash path: `Stop-Process` the renderer directly and confirm the brain exits on its own within ~4 s (two cycles); no orphan node/powershell from any cycle.
**Commit:** `feat: resident tray app wiring brain + renderer`

## Step 5: Hotkey tagging
**Files:** `src/renderer-win.ps1` (RegisterHotKey, tags.json writer), `src/brain.js` (tag-identities.json writer)
**What:** Ctrl+Alt+G appends `{hwnd, pid, taggedAt}` for the foreground window to tags.json; Ctrl+Alt+U removes it; the renderer also prunes entries whose window or process is gone. One writer per file: the brain NEVER writes tags.json; it resolves each tag once to the newest aura session's identity, frozen into tag-identities.json (keyed `hwnd:pid:taggedAt`), pruned when the tag goes. A tag made while NO aura session exists stays unresolved (no ring) and the brain retries every cycle until one appears. Hotkey registration failure (already taken) logs to the local log and continues (rule 6).
**Verify:** Tag a scratch Notepad window: ring appears in the newest session's repo color within one brain cycle; switching work to another repo does NOT change the tag's color (frozen); Ctrl+Alt+U clears it; closing the window prunes both files' entries; tags survive a full stop/start; with `--state` pointed at an empty state file a new tag stays unresolved with no ring, then resolves within one cycle after the real state path is restored; with Ctrl+Alt+G pre-registered by a scratch process the app still starts, rings still work, and the conflict is logged.
**Commit:** `feat: hotkey tagging with frozen tag identities`

## Step 6: Soak + ship docs
**Files:** `README.md` (quickstart), `docs/ARCHITECTURE.md` (only if drift), one-line Lane B pointer in aura's README (separate commit in aura).
**What:** Run the full app against the real desktop for 5+ minutes with at least 8 rings (palette temporarily widened via config to reach 8 if needed, plus scratch windows; restored after). Two CPU gates, because the spike number (0.72%) was ONE ring under motion: steady state, and a 30 s motion burst with ALL scratch ringed windows moved concurrently by the test script (the harness moves only windows it spawned; rule 4 binds product code). Measure both processes' CPU and working set at start and end. Document start, stop, tag keys, config, the OPT-IN autostart command (schtasks one-liner, documented but NOT registered; registering it is Keith's call), and the deliberate deferrals: mixed-DPI monitors and monitor hotplug are untested on this single-monitor box; the 30 ms rect re-poll self-corrects position but DPI-change correctness is not claimed.
**Verify:** Combined CPU under 3% sustained at steady state AND during the 30 s all-windows-moving burst; working sets flat (no growth over the soak); zero focus changes attributable to the overlay during the soak; stop leaves no trace. Screenshot of the ringed desktop for the record.
**Commit:** `docs: MVP quickstart + soak results` (aura repo: `docs: point Lane B section at aura-overlay`)
